# Recipes App — Technical Specification

Companion to [feature.md](feature.md). The data layer is detailed in [data-model.md](data-model.md).

## 1. Stack

| Concern | Choice |
|---|---|
| Framework | React Native + Expo (managed workflow, development builds) |
| Language | TypeScript (strict mode) |
| Navigation | Expo Router (file-based) |
| Database | SQLite via `expo-sqlite` |
| ORM / migrations | Drizzle ORM + `drizzle-kit` |
| Full-text search | SQLite FTS5 (raw SQL migration) |
| Images | `expo-image-picker`, `expo-image-manipulator`, `expo-file-system`, `expo-image` for display |
| Preferences | Deferred (not needed for P0); MMKV or `expo-sqlite/kv-store` when settings land |
| UI state | Zustand (ephemeral UI state only) |
| Data access in UI | Drizzle live queries (`useLiveQuery`) or TanStack Query over repositories |
| Forms | `react-hook-form` + `zod` |
| Drag to reorder | `react-native-reorderable-list` (or `react-native-draggable-flatlist`) |
| Testing | Jest (domain logic, repositories against in-memory SQLite), Maestro (E2E, later) |
| Lint / format | ESLint + Prettier |

Anything requiring native modules means using an Expo development build, not Expo Go.

## 2. Architecture

Layered, with dependencies pointing inward. The domain layer has no React or database imports.

```
UI (screens, components)
   ↓ uses
Hooks / view-models
   ↓ calls
Repositories (data layer: Drizzle queries, file storage)
   ↓ map rows ⇄ domain models
Domain (pure TypeScript: models, scaling, unit conversion, merging, parsing)
```

- **Domain**: pure functions and types. Fully unit-tested. This is where the risky logic lives.
- **Data**: repositories are the only code that touches Drizzle or the filesystem. They return domain models, never raw rows.
- **UI**: screens call hooks; hooks call repositories and domain functions. No SQL in components.

## 4. Local Storage

### 4.1 SQLite
- Single database file `recipes.db` in the app's document directory.
- `PRAGMA foreign_keys = ON` and WAL mode enabled on open.
- Migrations generated by `drizzle-kit` and applied at app start (before first render, behind a splash screen).
- FTS5 virtual table and triggers are written as a hand-authored migration since Drizzle does not model virtual tables.

### 4.2 Images
- Stored as files under `documentDirectory/photos/<photoId>.jpg`. The database stores only the relative path, so the absolute path is resolved at runtime (the app container path can change between installs and restores).
- On import: resize so the longest edge is at most 2048 px, JPEG at quality 0.8. Also generate a 400 px thumbnail for lists.
- Deleting a photo row deletes its files. A startup sweep removes orphaned files (best effort).

### 4.3 Preferences
- MMKV for unit system, theme, and default servings. Not for anything relational.

### 4.4 Backup and Export (P1)
- Export builds a zip: `recipes.json` (schema-versioned) plus `photos/`. Shared through the system share sheet.
- Import validates the version and merges by UUID. Existing IDs are skipped or overwritten depending on the user's choice.

## 5. Key Conventions

- **IDs**: UUID v7 strings (time-ordered), generated client-side. Enables sync and import/export with no ID collisions.
- **Timestamps**: integer epoch milliseconds (UTC). Every table has `createdAt` and `updatedAt`; user content tables have a nullable `deletedAt` (soft delete).
- **Ordering**: explicit integer `position` columns for ingredients, steps, and photos. Reordering rewrites positions in a single transaction.
- **Quantities**: numeric value plus unit key. Never store only free text. Original text is retained as `rawText` for display fallback.
- **Transactions**: every multi-row write (save recipe, generate shopping list) is one transaction.
- **Saving a recipe**: the editor saves the whole aggregate (recipe, ingredients, steps, tags) in one call, replacing child rows. Simple, and correct at this scale.

## 6. Feature Implementation Notes

### Recipe editor
- A form holding a full `RecipeDraft` in memory. Draft auto-save writes to MMKV as JSON every few seconds, and is cleared on successful save.
- Ingredient rows accept free text ("2 cups flour, sifted") that is parsed into quantity, unit, name, and note, with fields editable afterwards.

### Search
- FTS5 index over recipe title, description, tags, and ingredient names. Rebuilt per recipe on save through the repository (not DB triggers, since the content spans several tables).
- Prefix matching for search-as-you-type.

### Shopping list generation
1. User selects recipes and servings for each.
2. Domain `scaleIngredients` scales each recipe's ingredients.
3. Domain `mergeIngredients` combines compatible items (same normalized name, convertible units).
4. Result is persisted as a shopping list with items and per-recipe source rows, in one transaction.

Checked state lives on the item. Regenerating a list is a separate action and does not silently discard checked items.

## 7. Testing Strategy

- **Domain**: exhaustive unit tests for parsing, scaling, unit conversion, merging, and fraction formatting. This is the highest-value test suite.
- **Repositories**: integration tests against an in-memory SQLite (`better-sqlite3` with the Drizzle driver in Node) using the real migrations.
- **UI**: a few component tests for the editor; Maestro E2E for the core flow (create recipe, add photo, build shopping list) once the MVP stabilizes.

## 8. Milestones

1. **Foundation**: Expo project, TypeScript, lint, DB client, migrations, test setup.
2. **Domain**: models, quantity, units, scaling, merge, parser, with tests.
3. **Data layer**: schema, repositories, photo store, with tests.
4. **Recipe CRUD UI**: library, detail, editor, photos.
5. **Search**: FTS index and search UI.
6. **Shopping lists**: generate, manage, check off.
7. **MVP polish**: empty states, error handling, accessibility, app icon, store builds.
8. **P1 features**: cooking mode, import from URL, export/backup, collections.

## 9. Risks

| Risk | Mitigation |
|---|---|
| Ingredient parsing is messy ("a pinch of", "1 1/2", "2-3") | Keep `rawText` and let the user edit fields; the parser degrades to name-only |
| Unit merging gives wrong results (cups vs grams) | Only merge within the same dimension (volume or mass); never convert across without density data |
| Large photos fill storage | Resize and compress on import; thumbnails for lists |
| Schema changes after release | Migrations from day one; never edit a shipped migration |
| Expo/Drizzle API changes | Pin versions; isolate DB access behind repositories |
